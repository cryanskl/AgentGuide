第 1 关 · 入门

什么是 Agent？

一句话区分：LLM 负责「推理和生成」，Agent 系统负责「把模型放进可行动、可观察、可评测的环境里」。Agent 会对环境采取动作，并根据观察结果调整下一步——这是它和 Chatbot 的本质区别。

类型主要能力是否行动典型例子
Chatbot对话和回答否FAQ、知识问答
Workflow按固定步骤处理任务有，但流程固定分类 → 检索 → 生成 → 审核
Agent模型根据状态选择下一步动作有，路径可变研究助手、Coding Agent
Multi-Agent多个 Agent 通过角色或协议协作有planner + executor + reviewer
Anthropic 的工程实践强调：很多任务用 workflow 更稳，只有当任务路径难以提前写死、需要模型动态决策时，才需要更自主的 Agent。

🎮 练习 1：这是 Agent 吗？ ✓

看场景，判断它属于哪种系统。答错也没关系，看解释更重要。

🎮 练习 2：能力分级 L0 → L5 ✓

点击每个级别查看特征和示例。求职项目做到 L3–L4 就很有含金量，L5 复杂度和评测成本都很高，不建议新手一上来就做。看完全部 6 级即完成。

💬 面试怎么答：「什么是 Agent？」
Agent 是把 LLM 放进一个有状态、有工具、有反馈、有约束的执行循环中。它和普通 chatbot 的区别在于会对环境采取动作，并根据观察结果调整下一步。工程上我会重点设计 tool schema、context builder、loop controller、权限边界、trace 和 eval，而不是只写 prompt。（详见 01-what-is-agent.md）
第 2 关 · 核心循环

Agent Loop 与 ReAct

Agent 的最小闭环：Goal → 观察状态 → 思考/规划 → 调用工具行动 → 观察结果 → 停止 / 继续 / 请求人工。ReAct（Reasoning + Acting）就是这个循环的入门框架：先判断下一步，再调用工具，再根据观察结果继续。

🎮 练习 3：亲手驾驶一个 Agent Loop ✓

你来当 Agent 的「大脑」：任务是调研 Agent 评测基准。每一步从 3 个候选动作里选一个，选错会看到真实系统里对应的失败模式。右侧的 trace 会随你的操作实时生成——真实系统里存的就是这种可审计记录，而不是完整的 chain-of-thought。

🎮 练习 4：失败模式 ↔ 修复方案连线 ✓

先点左边的失败现象，再点右边对应的修复方案。这 6 种失败覆盖了 ReAct Agent 绝大多数线上事故。

💬 面试怎么答：「怎么设计 Agent Loop？」
我会把 ReAct 看成 Agent loop 的基础模式，但不会只依赖 prompt。工程实现里会加工具注册表、结构化输出、最大步数、重复动作检测、权限确认和 trace。对需要稳定性的业务流程，我会优先用 graph/workflow 承载确定步骤，只在开放决策点使用 ReAct。（详见 04-react-framework.md）
第 3 关 · 工具调用

Tool Calling 与 Tool Card

ReAct 失败常常不是模型不会推理，而是工具描述太差。工具要「小而清楚」：run_any_sql(query) 是坏工具，search_customer_orders(customer_id, date_from, date_to, status) 才是好工具——工具越泛化，模型越容易越权或误用。

🎮 练习 5：给任务选对工具 ✓

每个工具都带了 Use When / Do Not Use 描述。注意：正确答案不止取决于「能不能做」，还取决于「该不该做」。

🎮 练习 6：组装一张合格的 Tool Card ✓

一张合格的 Tool Card 至少要写清 7 件事。从下面的候选项里把它们全部挑出来（有 3 个是干扰项）。

💬 面试怎么答：「工具设计要注意什么？」
每个工具至少写清楚：什么时候用、什么时候不要用、输入 schema、输出 schema、错误类型、权限等级和示例。返回值要为模型优化——摘要、前 N 条、total_count、分页 token，而不是 10MB 原始 JSON。高风险动作（发邮件、付款、删除）必须 human-in-the-loop。（详见 Tool Card 模板）
第 4 关 · 上下文工程

Context Engineering

更长的上下文 ≠ 更好的响应。Karpathy 说，上下文工程是「在上下文窗口中填充恰到好处的信息，以支持下一步推理」的艺术。上下文会以 4 种方式失效：中毒、干扰、混淆、冲突。

🎮 练习 7：给「翻车的 Agent」做诊断 ✓

读症状，判断属于哪种上下文失效模式。这 4 种模式来自 Drew Breunig 的经典分析，也是面试高频题。

🎮 练习 8：8K 上下文预算，你来分配 ✓

同一个任务，不同的上下文组装策略，效果天差地别。为每一项选一种策略，目标：不超预算，质量分拉满。

💬 6 大修复技巧速查
① RAG：选择性检索相关信息，而不是全塞进去；② 工具装载（Tool Loadout）：按任务动态筛选工具，研究显示 46 个工具会让小模型失败，19 个就能成功；③ 上下文隔离（Quarantine）：多线程/子 Agent 各自独立上下文；④ 上下文修剪（Pruning）：删掉无关和过期信息；⑤ 上下文摘要（Summarization）：压缩长历史；⑥ 上下文卸载（Offloading）：把中间产物存到外部（scratchpad/文件），需要时再取。（详见 14-context-engineering.md）
第 5 关 · 记忆系统

Agent Memory

没有 Memory 的 Agent，第二轮就忘了你叫什么。推荐三层架构：工作记忆（当前会话最近若干轮，存内存）→ 情节记忆（本次会话关键信息，存向量库）→ 语义记忆（跨会话的长期偏好和知识，存知识图谱 + 向量库）。

🎮 练习 9：把信息归档到正确的记忆层 ✓

为每条信息选择它应该存放的记忆层。判断标准：它的生命周期有多长？跨不跨会话？

💬 面试怎么答：「什么值得存，什么时候忘？」
工作记忆容量有限（最近 10-20 轮），靠滑动窗口 + 摘要淘汰；情节记忆存本次会话的关键决定和中间产物，会话结束后提炼进语义层或丢弃；语义记忆存跨会话稳定的用户偏好和事实，写入前要做冲突检测和去重，并支持衰减/遗忘，否则过期偏好会变成上下文中毒源。（详见 15-agent-memory.md）
第 6 关 · 检索增强

RAG 全流程

RAG（Retrieval-Augmented Generation）的本质是信息管理：模型不知道你的私有数据，与其全部塞进上下文，不如按需检索最相关的片段。每次上下文窗口变大就有人喊「RAG 已死」，但精准检索恰恰在大窗口时代更重要。

🎮 练习 10：按顺序搭建 RAG 流水线 ✓

下面 7 个阶段被打乱了。按数据流动的正确顺序依次点击它们。点错会弹回，想想数据先经过谁。

🎮 练习 11：RAG 调参直觉题 ✓

3 道场景题，练的是「出了问题先动哪里」的工程直觉。

💬 面试怎么答：「RAG 效果差怎么排查？」
先分层定位：检索层看 recall（正确片段有没有被召回）→ 排序层看 top-k 里正确片段排第几（需要 rerank 吗）→ 生成层看模型有没有用上召回内容（引用检查）。切块大小、overlap、embedding 模型、混合检索（BM25 + 向量）、rerank 都是检索层的旋钮；不要一上来就换大模型。（详见 20-rag-full-pipeline.md）
第 7 关 · 协议与安全

MCP 协议与权限治理

MCP（Model Context Protocol）是 Agent 连接外部工具和数据源的标准接口层——「USB-C for AI tools」。它解决的不是「模型更聪明」，而是「工具怎么被发现、描述、调用和治理」。模型不应该直接访问数据库或 shell，而要通过 host/client 受控调用。

🎮 练习 12：MCP 六大角色连线 ✓

先点左边的角色，再点右边它的职责。调用链：User → Host → MCP Client → MCP Server → Tool/Resource → 结果回到 Model。

🎮 练习 13：给动作定权限等级 ✓

Low = 可直接调用；Medium = 记录 trace、限制范围；High = 必须 human-in-the-loop 人工确认。给每个动作选一个等级。

💬 面试怎么答：「MCP 是安全银弹吗？」
不是。MCP 解决的是标准化连接问题，安全治理仍要自己做：tool schema 收紧、server allowlist、最小权限、human-in-the-loop、把工具输出当不可信数据（防 prompt injection）、trace 里做 secret redaction。风险清单可参考 OWASP MCP Top 10。（详见 14-mcp-protocol.md）
